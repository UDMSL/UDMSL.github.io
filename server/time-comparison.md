## 해석과 한계

이 환경에서는 연결이 준비된 뒤 API 시각이 KRISS와 수 ms 수준으로 가까웠습니다. 그러나 이것은 **짧은 실측에서 관찰한 차이이며 절대 정확도나 서비스 보장 수치가 아닙니다**. NTP도 공인 계측 기준으로 사용한 것이 아니라 네트워크를 통한 추정값입니다. 특히 해외 경로 비대칭은 NICT 등 서버 간 차이에 영향을 줄 수 있으므로 특정 서버가 부정확하다고 단정할 수 없습니다.

NTP는 서버 수신·송신 시각을 포함하는 네 개의 타임스탬프로 서버 처리 시간을 제외할 수 있습니다. TimeAPI.io의 JSON에는 이 정보가 없어 전체 HTTPS 지연의 절반으로 근사하며, DNS/TLS 연결·서버 처리·경로 비대칭에 따른 오차가 남습니다. 초기 요청의 큰 차이는 이 한계를 보여 줍니다. RTT가 310 ms라고 해서 시계가 310 ms 틀리거나 반드시 ±155 ms 이내라는 뜻은 아닙니다. 이번 실측만으로 항상 10 ms 이내 또는 NTP와 동등하다고 보장할 수 없습니다. 엄밀한 경계 시각 일치가 필요하면 직접 NTP 동기화 방식이 유리합니다.

TimeAPI.io는 현재 무료라고 안내하며 모든 엔드포인트의 CORS를 지원합니다. 확인한 공개 문서에서는 수치로 된 정확도 보장이나 무료 서비스 SLA를 확인하지 못했습니다. [공식 FAQ](https://timeapi.io/home/faqs), [공식 변경 이력](https://timeapi.io/home/changelog), [NTP 시간 동기화 설명](https://www.ntp.org/ntpfaq/ntp-s-algo/).

## 페이지 적용

- 중계 서버 없이 브라우저가 UTC API를 직접 요청합니다. API 키나 추가 호스팅이 필요하지 않습니다.
- 초기·매 60초·탭 복귀·온라인 복귀·재동기화 버튼에서 각 3회 조회하고 최소 RTT 표본을 사용합니다. 5초를 넘는 응답과 잘못된 UTC 필드, Age가 있는 캐시 응답은 제외합니다.
- UTC 응답의 오프셋 없는 dateTime을 명시적으로 UTC로 해석합니다. 화면은 기존처럼 브라우저 시간대로 표시합니다.
- API 시각에 RTT 절반을 더하고 performance.now()로 이후 경과 시간을 계산하므로 기기의 현재 날짜·시각 수정에 의존하지 않습니다.
- 실패 시 마지막 동기화 시각으로 최대 15분 진행하며 경고합니다. 최초 실패 또는 유효 시간 만료 시 `--:--:--`로 표시합니다. NIST나 기기 시각으로 조용히 전환하지 않습니다. 현재 출처는 TimeAPI.io로 표시합니다.
- 기존 메모, Enter 줄바꿈, 글자 자동 크기, 좌우 배치, 초 반동, 12/24시간, 전체 화면을 유지합니다.

재측정: Node.js 24에서 `node scripts/compare-time.mjs`. 외부 HTTPS와 UDP 123이 허용된 네트워크가 필요하며 JSON 결과를 덮어씁니다. 이 문서의 표는 위 측정일의 결과입니다.
